请求头的训练数据 `data/v3-primary/real_train.jsonl` 共 936 条,按 `assign_folds`(seed 不变)切 5 折做折外 need 预测。开发折 = 第 0-2 折,测试折 = 第 3-4 折;参考集 = D-005 定稿的 200 条(`data/gold_candidates_claude.csv`)。

> 显式设置:need 头两级判定、分类头/检索都按线上默认(tfidf,检索编码器`tfidf`),软 need 阈值 0.7。只在开发折上选;测试折、参考集各只报一次,不用来调参(D-005)。

## 6. 结论

按任务卡的选法(约束内开发折需要工具召回最高),选中 **C2:bge-m3 need 头**:开发折召回 88.1%(基线 79.6%),精确率 87.2%(基线 78.8%),alpaca 误挂率 6.2%(基线 2.9%,门槛 +5 点)。


但它同时把 T-021 端到端主口径的**英文**严格 R@5 拉低:开发折 63.8% → 42.1%(-21.7 点),测试折 57.2% → 39.4%(-17.8 点);中文开发折 37.5% → 34.6%。原因是请求头只在中文请求上训练,语义编码器让英文请求的 need 判定明显变差。


**结论:本卡不改默认。**
选中的 C 需要额外的语义编码器:设成默认会让 `cli train` / 线上加载依赖语义模型(与 T-016/T-019「默认 tfidf、语义编码器可选、部署瘦身」的方向相反),而且上面这条英文退化必须先解决。建议单独立卡评估(含中英双语训练请求、部署重量)。


若只想要一条**零依赖**的改动,约束内的是 **A:none 阈值 0.55**:开发折召回 87.1%(基线 79.6%,+15 条/201 条真值要工具),精确率 76.4%(-2.4 点);参考集召回 81.0%(基线 75.5%);端到端与基线逐项相同(它只改 need 标签,附带候选的集合不变——软 need 已覆盖同一 p_none 区间)。它是决策规则改动而非建模改动,是否落地取决于把「漏判代价高于误报」(D-004)折算成多大召回偏好。
