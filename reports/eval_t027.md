# 能力域预测:分类头 + 检索结果投票(T-027)

真实目录 2405 个工具(双语索引),600 条 BFCL 请求;请求头按 5 折折外训练(`assign_folds`,seed 不变),开发折 = 第 0-2 折,测试折 = 第 3-4 折。

> 显式设置:分类头与检索都按线上默认(tfidf,双语索引,软过滤关,软 need 0.7,top_k=5);投票只在检索 Top-k 的 `domains` 上做,**不反馈进检索**(本卡只改能力域输出)。只在开发折上选;测试折与参考集各只报一次,不参与选择。

> 1 条样本 = 1/360 = 0.28 个百分点(开发折)。

> 复跑说明:标 ms 的数字(投票延迟)两次运行会变,其余数字逐字节相同。


## 0. 调查结论

**结论**:600 条 BFCL 是唯一有规模的集合,它的域来自金标工具的银标域,是**工具域**的代理;参考集的 147 条是唯一按**请求域**标的集合。两者对同一方法的结论可以完全不同(见第 3 节),所以开发折按 BFCL 选、参考集用来验伪。

**(2) 现状(开发折 360 条,BFCL 工具域)**:D0 基线主口径主域准确率 **24.4%**;`domains` 为空 **154/360(42.8%)**——这些行都是 need 头把该请求判成了 none(能力域头只在 need≠none 时才给域)。

**(3) 能力域现在被谁用**:真实目录这条链软过滤默认**关**(`Router(use_filter=False)`,见 `_snapshot_router` / `build_real_router`)。关掉后 `Router.route` 走 `catalog.retrieve(text, None, n)`,**不看** `domains`;need 来自 need 头;`requires_confirmation` 只看候选风险与 `actions`。所以当前 `domains` **只影响输出字段**(以及下游 agent 怎么用它),不影响检索与 need。本卡据此把投票只接到输出字段上,need 与检索候选逐字节不变(开发折摘要 `a1d2be664511`,见第 1 节约束)。


## 1. 候选对照(只比开发折,360 条)

## 4. 结论

- 开发折(BFCL 工具域)上,检索投票把主口径从 24.4% 提到 **83.6%**(+59.2 个点),远超 3 个点的改默认门槛;测试折同向(22.9% → 80.8%)。

- 但在**参考集(请求域)**上,同一个开发折主选是 32.7%,比 D0 的 40.8% **低 8.2 个点**。原因是开发折的金标是工具域、投票又是在被检索工具上做的(循环),这套数字没有转移到请求域。

- 按任务卡门槛,开发折确实高出 ≥ 3 个点;但参考集是唯一按请求域标注的集合,它显示开发折选出的配置**会变差**。以参考集为准,**本卡不改默认**:`domains` 仍由能力域头出,Router 没有接投票,`cli evaluate` / `cli route` 输出与改前逐字节一致(只有延迟会变)。

- 若将来要在请求域上用它,只能把融合权重推到头分布一侧(β→1 时退化成 D0,等于放弃投票);而"选哪个 β"只能在参考集上选——违反 D-005(参考集只报告)。应另立卡,并先扩一份请求域标注集来承担选参。是否值得做,留给 Claude / gu 决定,见 `.collab/reports/T-027.md` 开放问题。
